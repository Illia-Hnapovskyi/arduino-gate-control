# Arduino Gate Control: AI Maintainer Guide

This file applies to the entire repository. Read it before changing code. It is
the compact source of operational context for coding agents; `README.md` remains
the user-facing setup guide.

## 0. Sixty-second orientation

- Active app: Vite/React (`src/main.tsx` → `app/page.tsx`), not Next.js.
- Active backend: Vercel `api/stats.ts` → Neon Postgres; shared contract lives in
  `shared/gameStats.ts`.
- Start frontend work with `npm ci && npm run dev`; use `npx vercel dev` plus
  `DATABASE_URL` for real stats API work.
- Before handoff run `npm run check` and `git diff --check`.
- Keep firmware, serial parsing, translations, validation, and both Postgres
  schema copies synchronized when their contracts change.
- No cookies and no committed secrets. Profile codes are passwords.
- `worker/`, D1/Drizzle, Next.js, and vinext files are optional legacy paths,
  although they are still included in lint/type checking.

## 1. Project mission and current architecture

This repository contains a browser control panel for an Arduino UNO project
with three mutually exclusive device modes:

- gate control, including manual and ultrasonic automatic modes;
- servo-based ultrasonic radar with climate telemetry and music controls;
- the browser game “Space Defender”, controlled by keyboard, touch, a virtual
  joystick, or the physical Arduino joystick.

The active production shape is:

```text
Browser (React 19 + Vite)
  ├─ Web Serial at 115200 baud ── Arduino UNO firmware
  ├─ localStorage ─────────────── language, profile secret, offline run queue
  └─ /api/stats ───────────────── Vercel Function
                                      └─ Neon Postgres via DATABASE_URL
```

Vercel builds the frontend into `dist/` with `npm run build`. The server-side
statistics endpoint is `api/stats.ts`. The application does not currently use
Next.js as its frontend runtime, even though some Next.js/vinext/Cloudflare
scaffolding remains in the repository.

Active stack snapshot (keep `package.json` and the lockfile authoritative):

- React `19.2.8` and React DOM `19.2.8`;
- Vite `8.2.0` with `@vitejs/plugin-react`;
- TypeScript `5.9.3` in strict/no-emit mode;
- `@neondatabase/serverless` `^1.1.0` for the active Postgres path;
- hand-written global CSS processed by Tailwind/PostCSS, browser
  Canvas/Web Audio/Web Serial, and Node's built-in tests.

## 2. Non-negotiable product and safety rules

- Preserve demo mode. The UI must remain usable without an Arduino and in
  browsers without Web Serial.
- Do not add cookies unless the user explicitly approves them and a visible
  cookie-consent/help UI is added at the same time. The current implementation
  intentionally uses no cookies and sends stats requests with
  `credentials: "omit"`.
- Never commit database URLs, access codes, `RATE_LIMIT_SECRET`, temporary Neon
  claim URLs, user data, or other credentials.
- Treat a profile access code as a password. Never log it. The database stores
  only its SHA-256 digest.
- Keep browser validation, API validation, and database constraints compatible.
  A valid run generated by the game must never be rejected by the server.
- Do not restore a shot-rate-derived score ceiling without first unifying all
  game clocks. Firing uses wall-clock animation timestamps while recorded active
  duration uses a capped physics delta; a shot-rate ceiling rejected legitimate
  low-FPS runs in the past.
- Whenever the Postgres schema changes, update both the runtime schema in
  `api/stats.ts` and `db/migrations/0001_game_stats.sql`.
- Keep all three UI languages (`uk`, `de`, `en`) at key parity.
- Preserve unrelated user changes and inspect `git status` before editing.
- Do not rewrite shared Git history or use destructive Git commands for normal
  work. Prefer a new commit and `git revert` for rollback.
- Hardware safety matters: disconnect USB before rewiring, and never apply 9 V
  to 5 V, D2-D7, sensors, joystick, servo, or buzzers.

## 4. Local workflow

Requirements:

- Node.js `>=22.13.0` (see `package.json`);
- npm and the committed `package-lock.json`;
- Chrome or Edge for physical Web Serial testing;
- a Postgres/Neon `DATABASE_URL` only when testing cloud statistics.

Install and run the frontend only:

```bash
npm ci
npm run dev
```

`npm run dev` starts Vite. It does **not** execute `api/stats.ts`; profile data
can be created locally and queued, but the UI will report a sync error until the
full API is available.

Run the Vercel frontend and API together:

```bash
DATABASE_URL='postgresql://...' RATE_LIMIT_SECRET='a-long-random-secret' npx vercel dev
```

Prefer environment files or the Vercel CLI environment store over putting
secrets directly in shell history. `RATE_LIMIT_SECRET` is recommended to be at
least 32 random characters. If omitted, the API uses `DATABASE_URL` as the HMAC
key without storing or returning that URL.

Useful commands:

```bash
npm run lint
npm run typecheck
npm run build
npm test
npm run check
npm audit --omit=dev
```

`npm test` intentionally builds first, then uses Node’s built-in test runner
with TypeScript type stripping. There is currently no jsdom/Playwright hook-test
stack in the repository.

## 5. Frontend state and browser behavior

`app/page.tsx` is a single stateful application rather than a routed SPA. The
top-level tabs switch between the control panel and the game. Entering/leaving
the game tab stops conflicting Arduino modes.

Language state:

- supported values: `uk`, `de`, `en`;
- localStorage key: `arduino-gate-language`;
- same-tab updates use `arduino-gate-language-change`;
- cross-tab updates use the browser `storage` event.

Game profile state:

- localStorage key: `arduino-gate-game-stats:v1`;
- the stored object contains a schema version, local profile, pending runs, and
  recently known run IDs;
- local writes and optimistic totals happen synchronously before network sync;
- online reconnect and the `online` event retry queued changes;
- a profile can be opened on another device only with its access code;
- “forget profile” removes only this browser’s local copy. It does not delete
  the remote profile;
- the browser remembers 100 recent run IDs; the server retains the newest 512
  per profile for idempotency while keeping lifetime aggregates.

Synchronization ordering is deliberate. For a confirmed profile with pending
mutations, flush rename/run operations before doing an idle profile refresh.
This prevents double-counting when a prior record request reached Postgres but
its HTTP response was lost.

## 6. Game and run invariants

Important game mechanics in `app/GamePanel.tsx`:

- initial lives: 3;
- level range: 1-9;
- level increases every 22 seconds of recorded active game time;
- destroying an asteroid adds `10 * currentLevel` points;
- shot cooldown: 220 ms, but do not use this alone for server plausibility for
  the clock reason described above;
- physics frame delta is capped at 34 ms;
- a profile is required before a run can start.

Each start creates a cryptographically random `runId`. An active run is queued
exactly once when the player reaches game over, presses stop, disconnects,
leaves/unmounts the game, or closes a non-bfcache page. `recordActiveRun` clears
the active ID before calling `recordRun`, and the server additionally enforces
`UNIQUE (player_id, run_id)`.

Shared run validation currently requires:

- `runId`: 8-64 ASCII letters, digits, `_`, or `-`;
- `score`: safe integer from 0 through 100,000,000 and divisible by 10;
- `level`: safe integer from 1 through 9;
- `durationMs`: safe integer from 0 through 21,600,000 (six hours);
- level no greater than `min(9, 1 + floor(durationMs / 22000))`.

If mechanics change, change `GamePanel`, `shared/gameStats.ts`, API validation,
SQL checks, tests, and relevant copy together.

## 7. Profile and statistics contract

Profile nicknames:

- normalized with Unicode NFKC, trimmed, and internal whitespace collapsed;
- 2-20 Unicode code points;
- letters, combining marks, numbers, spaces, `_`, `.`, and `-` only;
- must contain at least one letter or number;
- unique case-insensitively in Postgres;
- a localized random nickname has an adjective plus six digits.

Access codes:

- 20 cryptographically random Crockford-style Base32 characters;
- displayed as four groups of five characters;
- spaces and hyphens are ignored on input;
- ambiguous `O`, `I`, and `L` normalize to `0`, `1`, and `1`;
- raw value stays in the browser and request only; Postgres stores SHA-256.

Public API at `/api/stats`:

- `GET`: returns the top 25 leaderboard entries, excluding zero-game profiles;
- `POST { action: "create", accessCode, nickname?, language }`;
- `POST { action: "connect", accessCode }`;
- `POST { action: "rename", accessCode, nickname }`;
- `POST { action: "record", accessCode, runId, score, level, durationMs }`.

Use the request/response types from `shared/gameStats.ts`; do not create a second
slightly different contract. Responses are JSON with `no-store` headers. Only
GET and POST are accepted, and request bodies are limited to 8 KiB.

The profile aggregates are:

- nickname;
- games played;
- total score;
- high score;
- highest level;
- total active duration;
- last update timestamp.

## 8. Postgres schema and API security

Active tables:

- `game_players`: hashed access code, nickname/language, and lifetime aggregates;
- `game_runs`: recent idempotency records linked to a player;
- `game_rate_limits`: HMAC-pseudonymized fixed-window counters.

`api/stats.ts` initializes missing tables/indexes under a Postgres advisory lock.
The Neon role therefore needs schema creation privileges on first request. The
checked-in SQL migration is safe for a fresh database, but `CREATE IF NOT
EXISTS` does not evolve an already-existing incompatible schema. For a future
schema change, add explicit migration/ALTER logic instead of assuming the
runtime initializer upgrades old tables.

Current fixed one-hour mutation limits:

- 600 total mutations per Vercel client IP;
- 30 create/create-upsert operations per client IP;
- 240 recorded runs per profile;
- 30 rename/create-upsert operations per profile.

Rate-limit scopes are HMAC-SHA-256 values. The raw
`x-vercel-forwarded-for` address is never inserted into Postgres. A blocked
request returns HTTP 429 and `Retry-After`. Counter rows older than two days are
periodically deleted.

The leaderboard is intentionally casual. Browser clients report results, so
range/format checks and rate limiting reduce obvious abuse but are not tournament
anti-cheat. Do not claim the scores are cryptographically verified. A real
competitive mode would need server-issued run sessions/proofs or authoritative
server gameplay.

## 9. Web Serial and Arduino protocol

The browser opens the selected port at 115200 baud. Opening an Arduino UNO port
usually resets the board, so the frontend waits about 1.7 seconds, sends
`STATUS`, waits for valid telemetry, applies current configuration, and verifies
the echoed state before marking the connection as ready.

Commands are newline-terminated ASCII. The firmware command buffer accepts at
most 40 non-CR characters, so keep commands short.

Main commands:

| Command | Meaning/range |
| --- | --- |
| `STATUS` | Send telemetry immediately. |
| `OPEN`, `CLOSE` | Stop radar and move the gate. |
| `ANGLE:n` | Manual servo angle, constrained to 10-90°. |
| `AUTO:0|1` | Disable/enable automatic gate mode. |
| `LIMIT:n` | Detection threshold, constrained to 8-80 cm. |
| `HOLD:n` | Gate-open hold time, constrained to 1000-10000 ms. |
| `RADAR:0|1` | Stop/start radar mode. |
| `SCAN:n` | Radar step interval, constrained to 30-100 ms. |
| `MUSIC:1..3`, `MUSIC:STOP` | Built-in passive-buzzer melodies. |
| `GAME:1`, `GAME:0` | Enter/leave game mode. |
| `GAME:PAUSE`, `GAME:RESUME`, `GAME:OVER` | Game/audio state. |
| `GAME:SOUND:0|1` | Disable/enable game audio. |
| `TRACK:START`, `TRACK:STOP` | Control browser-streamed live track mode. |
| `TRACK:TONE:frequency:duration` | Passive-buzzer tone; 0-4000 Hz and 20-1000 ms. |
| `SFX:VOLUME:percent` | Active-buzzer PWM volume, 0-100%. |
| `SFX:name` | Play a named game sound effect. |

Telemetry is one JSON object per line with these fields:

```text
distance: number | null       angle: number
device: "gate" | "radar" | "game"
mode: "manual" | "auto"      gate: "open" | "closed"
limit: number                 hold: number (ms)
scanSpeed: number             music: 0 | 1 | 2 | 3
temperature: number | null    humidity: number | null
dhtOk: boolean                joystickX: number
joystickY: number             joystickPressed: boolean
gameSound: boolean
```

Normal telemetry interval is 250 ms, radar is 100 ms, and game mode is 50 ms.
Keep the firmware output and `GateMessage` parsing in `app/page.tsx` compatible.

Protocol caveats worth preserving:

- there are no per-command acknowledgements; state-changing commands are
  confirmed through later telemetry;
- firmware emits `gameSound`, but the current `GateMessage` type ignores it;
- the TypeScript gate status type permits `"moving"`, but current firmware emits
  only `"open"` (angle at least 55°) or `"closed"`;
- ultrasonic measurement is suspended in game mode, so `distance` may contain
  the last gate/radar reading while the game is active;
- `TRACK:*` has no firmware-side game-mode guard. The browser must keep it scoped
  to the game player;
- `TRACK:STOP` intentionally leaves live-track mode selected so silence does not
  fall back to the built-in game tune;
- the UI uses `ANGLE:n` for manual movement even though firmware also supports
  `OPEN` and `CLOSE`.

## 10. Hardware map

| Component | Arduino UNO connection |
| --- | --- |
| SG90 servo signal | D9 |
| HC-SR04 TRIG / ECHO | D7 / D6 |
| Passive buzzer through 100 Ω resistor | D3 |
| Active buzzer (PWM volume) | D5 |
| DHT11 data | D2 |
| Joystick VRx / VRy / switch | A0 / A1 / D4 |

Servo constants are 10° closed, 90° open, and a 15-165° sweep in radar mode.
The joystick switch uses `INPUT_PULLUP`. The supplied three-pin DHT11 module
does not need a separate library or extra pull-up resistor in this firmware.

Firmware defaults are manual gate mode, a 25 cm threshold, 3000 ms hold time,
45 ms radar step, centered joystick values around 512, game sound enabled, and
active-buzzer PWM duty 71/255 (about 28%). Gate distance reads happen about every
120 ms, radar reads every 65 ms, radar advances in 2° steps, and climate is read
about every 2200 ms. The HC-SR04 pulse timeout is 24,000 µs.

Remove the physical gate arm before using the 15-165° radar sweep so it cannot
strike nearby objects. A heavier servo mechanism should use a separate regulated
5 V supply with common ground; stop immediately if the UNO resets or the servo
jitters.

When changing pins, commands, constraints, or hardware behavior, update all of:

- `public/arduino-smart-gate.ino`;
- `public/README-UK.md`;
- UI labels/diagrams in `app/page.tsx` and `app/i18n.ts`;
- artifact tests where applicable.

## 11. UI, CSS, and localization rules

- `app/globals.css` is intentionally monolithic. Reuse existing variables,
  spacing, buttons, cards, and focus behavior before inventing a second system.
- The stylesheet starts with `@import "tailwindcss"`, and PostCSS uses
  `@tailwindcss/postcss`; keep those build dependencies even though most visual
  rules are hand-written global CSS rather than utility classes.
- Responsive breakpoints currently exist at 1120, 980, 640, 480, and 430 px.
  Stats switch from two columns to one at 980 px; forms and stats compact again
  at 640 px.
- Check both approximately 1440 px desktop and 390 px mobile widths after
  meaningful UI changes. There must be no horizontal page overflow.
- Preserve keyboard and touch controls, visible focus, screen-reader labels, and
  `prefers-reduced-motion` behavior.
- Add every user-facing string to all `uk`, `de`, and `en` sections. The
  translation parity test must remain green.
- Do not put user-provided nicknames into raw HTML. Render them through React
  text nodes as the current UI does.

## 12. Deployment

Production prerequisites managed outside Git:

- a Vercel project connected to this repository;
- a Neon Postgres integration or manually provisioned Neon database;
- `DATABASE_URL` in every Vercel environment that needs shared statistics;
- preferably `RATE_LIMIT_SECRET` in the same environments;
- a redeploy after environment changes.

Without `DATABASE_URL`, `/api/stats` intentionally returns HTTP 503 with
`DATABASE_NOT_CONFIGURED`; the browser keeps local profile/runs and shows a sync
error. Do not silently pretend cross-device persistence is active in that state.

The ordinary deployment path is defined by `vercel.json`:

```text
buildCommand: npm run build
outputDirectory: dist
```

Files under `api/` are deployed as Vercel Functions alongside the Vite output.

For database/API changes, perform at least one real integration pass against an
empty disposable Postgres/Neon database:

1. GET an empty leaderboard;
2. create a profile;
3. connect with its access code as a second client;
4. record a valid run and retry the same `runId`;
5. confirm totals increment once;
6. rename and verify the leaderboard;
7. verify invalid data and rate limiting;
8. ensure no connection string, access code, raw IP, or claim URL reaches logs or Git.

## 13. Legacy and optional infrastructure

Do not mistake these for the active Vercel path:

- `worker/index.ts`: optional Cloudflare/vinext worker entry;
- `db/index.ts`, `db/schema.ts`, `drizzle.config.ts`, `examples/d1/`: optional
  Cloudflare D1/Drizzle example infrastructure, not the Neon stats schema;
- `next.config.ts`, `app/chatgpt-auth.ts`, `build/`, and `scripts/`: retained
  Next.js/OpenAI Sites/vinext support and build tooling;
- Cloudflare, Next.js, Drizzle, and vinext dependencies remain in
  `package.json` for that optional infrastructure.

The root TypeScript and ESLint configurations still inspect most repository
TypeScript, including optional code. A broken legacy file or prematurely removed
dependency can therefore fail the active project's `npm run check` even when it
is not executed by Vercel.

Do not delete or migrate the optional stack unless the task explicitly targets
it. Do not implement current game statistics in `db/schema.ts`; the live source
is `api/stats.ts` plus `db/migrations/0001_game_stats.sql`.

The primary remote is `origin` and the active branch is `main`. The cross-device
statistics feature was introduced in commit `36d21db`.

Remote rollback references created before that feature:

- tag: `pre-cross-device-stats-20260731`;
- branch: `backup/pre-cross-device-stats-20260731`;
- target commit: `725492683dd7c5b4ba34ebd59a5cfe36f71cb8dc`.

For a shared deployed branch, prefer a history-preserving rollback:

```bash

```

Use the rollback tag/branch for inspection or recovery, not as an excuse to
discard later unrelated work. Before handing off, report the exact commit, test
results, deployment prerequisites, and any external step you could not perform.

## 15. Known limitations

- Production cross-device sync cannot work until Vercel has a valid
  `DATABASE_URL`; that secret is intentionally absent from Git.
- The leaderboard is based on client-reported browser runs and is not suitable
  for prizes or adversarial competition.
- There is no email/account recovery. Losing the access code means losing
  access to the remote profile.
- There is no remote profile-deletion endpoint; “forget” is local only.
- Plain Vite development does not run Vercel Functions.
- Web Serial requires a compatible Chromium browser and a secure context; demo
  mode is the fallback.
- Runtime `CREATE IF NOT EXISTS` is convenient for a fresh database but is not a
  complete long-term migration system.
- Automated tests currently do not execute React hooks/UI interactions, physical
  Web Serial, or a live Neon database. Use the manual/real integration checks in
  this guide for changes in those areas.

## 16. Definition of done

Before considering a change complete:

1. Inspect the final diff and confirm no unrelated files or secrets are present.
2. Run `npm run check` and `git diff --check`.
3. Run `npm audit --omit=dev` when dependencies changed.
4. Verify all three languages when copy or UI structure changed.
5. Verify desktop/mobile layout when CSS or components changed.
6. Verify both demo mode and physical-connection behavior when serial/game code changed.
7. Run a real disposable-Postgres API flow when persistence, SQL, validation, or rate limiting changed.
8. Update this file and `README.md` whenever architecture, commands, deployment,
   environment variables, protocol, or rollback procedures change.
